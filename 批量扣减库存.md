推荐方案是：先按固定顺序一次性锁住所有库存行，在锁内校验并计算流水，然后使用一条批量 `UPDATE` 更新全部库存。

这样可以把原来的：

```
1 次库存查询 + N 次库存 UPDATE + 1 次扣减后库存查询
```

优化成：

```
1 次 SELECT ... FOR UPDATE
1 次批量 UPDATE
```

同时保证库存和流水一致。

## 一、推荐执行流程

事务内按下面的顺序执行：

```
1. 查询商品快照
2. 按 productId 排序
3. SELECT ... FOR UPDATE 批量锁定库存
4. 校验库存记录是否存在、库存是否充足
5. 在内存计算 beforeQuantity 和 afterQuantity
6. 一条 SQL 批量更新库存
7. 保存订单主表
8. 批量保存订单明细
9. 使用第 5 步的结果批量保存库存流水
10. 提交事务，释放库存行锁
```

关键点是：Java 中的库存判断发生在库存行已经加排他锁之后，所以不是危险的“普通查询后再扣减”。

## 二、增加批量锁定库存方法

### Mapper

```
public interface ProductStockMapper extends BaseMapper<ProductStock> {

```

建议定义一个专门的内部参数：

```
public record StockDeduction(
        Long productId,
        Integer quantity

}
```

不要让库存 Mapper 直接依赖订单请求 DTO。

## 三、批量加锁 SQL

```
<select id="selectByProductIdsForUpdate"
        resultMap="BaseResultMap">
    SELECT
        id,
        product_id,
        available_quantity,
        total_out_quantity,
        version
    FROM product_stock
    WHERE is_deleted = 0
      AND product_id IN
    <foreach collection="productIds"
             item="productId"
             open="("
             separator=","
             close=")">
        #{productId}
    </foreach>
    ORDER BY product_id
    FOR UPDATE
</select>
```

这里有两个核心作用：

- `FOR UPDATE`：给查询到的库存行加排他锁，直到事务提交或回滚。
- `ORDER BY product_id`：所有创建订单事务都按相同顺序获取锁，降低死锁概率。

`product_stock.product_id` 必须有唯一索引。你当前表结构已有：

```
UNIQUE KEY uk_product_stock_product_id (product_id)
```

所以该查询可以通过索引定位。

## 四、锁内校验并计算流水

建议定义扣减结果：

```
private record StockDeductionResult(
        long productId,
        int quantity,
        int beforeQuantity,
        int afterQuantity
) {
}
```

实现：

```
private List<StockDeductionResult> lockAndCalculateStock(
        List<OrderCreateItemRequest> sortedItems) {

    List<Long> productIds = sortedItems.stream()
            .map(OrderCreateItemRequest::productId)
            .toList();

    List<ProductStock> lockedStocks =
            productStockMapper.selectByProductIdsForUpdate(productIds);

    Map<Long, ProductStock> lockedStocksByProductId =
            lockedStocks.stream()
                    .collect(Collectors.toMap(
                            ProductStock::getProductId,
                            Function.identity()
                    ));

    List<StockDeductionResult> results =
            new ArrayList<>(sortedItems.size());

    for (OrderCreateItemRequest item : sortedItems) {
        ProductStock lockedStock =
                lockedStocksByProductId.get(item.productId());

        if (lockedStock == null) {
            throw new BusinessException(ErrorCode.STOCK_NOT_FOUND);
        }

        int beforeQuantity = lockedStock.getAvailableQuantity();
        int deductionQuantity = item.quantity();

        if (beforeQuantity < deductionQuantity) {
            throw new BusinessException(ErrorCode.STOCK_NOT_ENOUGH);
        }

        int afterQuantity = beforeQuantity - deductionQuantity;

        results.add(new StockDeductionResult(
                item.productId(),
                deductionQuantity,
                beforeQuantity,
                afterQuantity
        ));
    }

    return results;
}
```

此时数据安全的原因是：

```
库存行已经由当前事务通过 FOR UPDATE 锁定
其他事务不能修改这些库存行
所以 beforeQuantity 在当前事务提交前不会被别人改变
```

## 五、使用一条 SQL 批量扣减库存

MySQL 可以通过 `CASE WHEN` 一次更新多行：

```
<update id="batchDeductStock">
    UPDATE product_stock
    SET
        available_quantity =
        CASE product_id
            <foreach collection="items" item="item">
                WHEN #{item.productId}
                THEN available_quantity - #{item.quantity}
            </foreach>
            ELSE available_quantity
        END,

        total_out_quantity =
        CASE product_id
            <foreach collection="items" item="item">
                WHEN #{item.productId}
                THEN total_out_quantity + #{item.quantity}
            </foreach>
            ELSE total_out_quantity
        END,

        version = version + 1

    WHERE is_deleted = 0
      AND
      <foreach collection="items"
               item="item"
               open="("
               separator=" OR "
               close=")">
          (
              product_id = #{item.productId}
              AND available_quantity >= #{item.quantity}
          )
      </foreach>
</update>
```

Java 调用：

```
List<StockDeduction> deductions = stockResults.stream()
        .map(result -> new StockDeduction(
                result.productId(),
                result.quantity()
        ))
        .toList();

int affectedRows = productStockMapper.batchDeductStock(deductions);

if (affectedRows != deductions.size()) {
    throw new BusinessException(
            ErrorCode.CONCURRENT_UPDATE_FAILED,
            "库存批量扣减影响行数异常"
    );
}
```

即使前面已经锁定并校验，这里仍然保留：

```
available_quantity >= quantity
```

这是数据库层最后一道防线。以后即使某段代码错误地绕过前置校验，SQL 本身也不会把库存扣成负数。

## 六、流水不再重新查询库存

你当前扣减后又查询了一次库存：

```
loadStocksByProductId(...)
```

优化后不需要这个查询，因为在行锁内已经计算出：

```
beforeQuantity
afterQuantity
```

直接根据 `StockDeductionResult` 创建流水：

```
private void createAndPersistStockFlows(
        List<StockDeductionResult> stockResults,
        Map<Long, Product> productsById,
        OrderInfo order,
        LocalDateTime now) {

    List<StockFlow> flows = new ArrayList<>(stockResults.size());

    for (StockDeductionResult result : stockResults) {
        Product product = productsById.get(result.productId());

        StockFlow flow = new StockFlow();
        flow.setId(IdWorker.getId());
        flow.setProductId(result.productId());
        flow.setSkuCode(product.getSkuCode());
        flow.setBizNo(order.getOrderNo());
        flow.setBizType(StockFlowBizType.ORDER_DEDUCT.getCode());
        flow.setChangeQuantity(-result.quantity());
        flow.setBeforeQuantity(result.beforeQuantity());
        flow.setAfterQuantity(result.afterQuantity());
        flow.setOperatorId(order.getBuyerId());
        flow.setOperatorType(OperatorType.USER.getCode());
        flow.setCreateTime(now);
        flow.setUpdateTime(now);

        flows.add(flow);
    }

    int insertedRows = stockFlowMapper.batchInsert(flows);

    if (insertedRows != flows.size()) {
        throw new BusinessException(
                ErrorCode.STOCK_FLOW_PERSIST_FAILED
        );
    }
}
```

## 七、Service 主流程调整

大致改成：

```
@Override
@Transactional(rollbackFor = Exception.class)
public OrderCreateResponse createOrder(
        OrderCreateRequest request) {

    LocalDateTime now = LocalDateTime.now();

    List<OrderCreateItemRequest> sortedItems =
            normalizeItems(request.items());

    Map<Long, Product> productsById =
            loadAndValidateProducts(sortedItems);

    CalculatedOrder calculatedOrder =
            calculateOrder(sortedItems, productsById);

    // 一次查询并锁定全部库存，在锁内计算前后库存
    List<StockDeductionResult> stockResults =
            lockAndCalculateStock(sortedItems);

    // 一条 SQL 扣减所有库存
    batchDeductStock(stockResults);

    OrderInfo order = createAndPersistOrder(
            request,
            calculatedOrder,
            now
    );

    createAndPersistOrderItems(
            order,
            calculatedOrder,
            now
    );

    // 不再查询扣减后的库存
    createAndPersistStockFlows(
            stockResults,
            productsById,
            order,
            now
    );

    return OrderCreateResponse.from(order);
}
```

## 八、为什么这样不会超卖

假设库存为 10，两个事务分别购买 8：

```
事务A：SELECT FOR UPDATE，拿到行锁，读取库存10
事务B：SELECT FOR UPDATE，等待事务A释放行锁
事务A：计算 10 → 2，更新库存，写流水，提交
事务B：拿到锁，读取库存2
事务B：发现 2 < 8，抛出库存不足
```

最终只有事务A成功，不会出现两个事务都基于库存10进行扣减。

## 九、需要注意的限制

不要把批量锁定方法写成普通查询：

```
SELECT ... WHERE product_id IN (...)
```

然后依赖 Java 校验。没有 `FOR UPDATE` 时，两个事务可以同时读取相同库存，Java 判断会失去并发安全性。

另外，所有修改 `product_stock` 的业务——创建订单、取消订单、人工调整库存——都必须遵守统一的加锁顺序。只优化创建订单而其他入口无序加锁，仍可能发生死锁。

对于当前最多 100 种商品的限制，`CASE WHEN` 批量更新是可行方案。如果实际订单通常只有 1～5 种商品，原来的原子单行 UPDATE 也未必是性能瓶颈，应先压测再决定是否引入这套复杂度。
